# CENTRAL-ONE development recovery runbook

**Status:** Disposable Central recovery rehearsal only. Production recovery, live cutover, and customer/POS restore are not commissioned.

## Recovery boundaries

Central control-plane recovery is separate from customer-edge/POS data restore. The `CUSTOMER_RESTORE_NOT_SUPPORTED` response is an intentional edge deferral and is not evidence of Central recovery. Central recovery must restore the Central database, schema/privileges, object metadata and owned ciphertext files, then verify invariants. V3 also recovers the protected development signer under its Windows DPAPI CurrentUser boundary and starts the actual Central host/outbox worker twice against the restored disposable target. Change236 separately validates one explicit 21-to-23 schema transition; it does not certify every supported-release path or rollback. This does not certify production key custody, full browser/API recovery, production recovery objectives, or live cutover.

Never export customer private keys or plaintext customer data. Do not claim Central can decrypt POS backups. Do not invent a backup-upload API: use only routes verified from the current controller source and route inventory.

## Supported local rehearsal

Use `scripts/central/Invoke-CentralDisposableRecoveryRehearsal.ps1` and `docs/central/CENTRAL_RECOVERY_REHEARSAL.md`. The script requires:

- An already owned disposable PostgreSQL 18 loopback source, with live process/binary/version/data-directory/port, postmaster file, marker, listener, database, runtime role, migration role and database-administration role all matching.
- Explicit runtime, migration, and database-admin connection strings loaded from the authorized local secret store. The admin credential is for the cluster's maintenance database; do not infer or copy its password from another role.
- Disjoint, existing, explicitly owned Central development roots; a fresh absent evidence directory; and a separately named disposable restore database matching the script's `central_restore_*` constraint.
- For backup capture, a current quiescence proof generated by the companion quiescence procedure and binding the actual coordinator, source database/process, zero active owned writers, and process-inventory evidence. For restore-only, the bundle manifest hash must be checked against its separately recorded SHA-256.

The script has mandatory `-TargetDatabase` and `-EvidenceRoot` parameters. It accepts `-QuiescenceProofPath` and `-RestoreBundlePath` / `-ExpectedBundleManifestSha256` for the corresponding modes. It refuses a pre-existing evidence root, mismatched target identity, unowned roots, stale proof, forbidden database/port, escaped storage path, altered bundle, or failed integrity/invariant check. Read the script and companion runbook before invocation; do not copy commands containing historical credentials or identifiers.

The rehearsal creates a new target database and evidence under the explicitly owned disposable roots. It does not terminate arbitrary API/PostgreSQL processes or recursively delete source data. Preserve the backup bundle, manifest, command inventory, database comparisons and result manifest. Any cleanup is a separate operation requiring fresh exact-path and ownership verification.
